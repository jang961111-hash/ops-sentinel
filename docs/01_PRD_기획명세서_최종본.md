## 2. 문제 정의 (Why)

현업 AIOps는 "장애가 난 뒤 사람이 로그를 뒤지는" 방식에서 "시스템이 스스로 이상을 감지·판단·조치하고, 그 판단 근거를 사람이 사후 검증할 수 있게 남기는" 방식으로 이동하고 있다. 이번 과제에서 흔한 "쇼핑몰+락 제어" 패턴 대신, **판단의 자동화 + 판단 근거의 검증 가능성**이라는 축으로 차별화한다.

## 3. 목표 / 비목표

**목표**
- 규칙 기반 이상탐지 → 사건(Incident) 자동 생성 → 조치(Action) 자동 기록
- 모든 처리 과정을 AOP로 감사로그(AuditLog)에 100% 기록 (성공/실패 무관)
- OpenAI API로 "왜 이 조치를 했는지" 자연어 판단근거 생성 (실패 시 안전한 폴백)
- JPA(CRUD)+MyBatis(집계) 역할 분리, 동시성 제어(중복 사건 방지)

**비목표**
- 실제 물리 인프라 연동 (전부 시뮬레이션 데이터)
- MSA 분리, K8s, 실서버 배포
- 정식 프론트엔드(SPA) — Swagger UI + 최소 정적 대시보드로 대체

## 3-1. 아키텍처 결정 (Architecture Decision Record)

| 옵션 | 채택 여부 | 근거 |
|---|---|---|
| **모듈러 모놀리식** (도메인별 패키지 분리, 단일 배포단위) | ✅ 채택 | 혼자·제한시간 안에 완성해야 하는 조건에서 서비스 간 통신·트랜잭션 분산 문제 없이 "구조는 잘 나뉘어 있다"는 신호를 줄 수 있는 유일한 현실적 선택. 실제로 조사한 동기 레포 중 최상위권(xixvivji)도 이 방식(Spring Modulith) 채택 |
| MSA (서비스 완전 분리) | ❌ 기각 | 서비스 간 통신·분산 트랜잭션·배포 파이프라인까지 혼자 감당하기엔 리스크 대비 이득이 작음. 시간이 남아도 우선순위 최하위(P3) |
| 단순 레이어드 모놀리식 (도메인 구분 없이 Controller/Service/Repository만) | ❌ 기각 | 대부분의 동기 레포가 이 수준이라 차별화가 안 됨 |

**패키지 구조**: `resource / metric / incident / audit / analytics / common` 도메인별 패키지, 각 패키지 내부에 `web(Controller) / service / repository / entity` 분리. 도메인 간 직접 참조 최소화(서비스 인터페이스로만 통신) — MSA 전환이 필요해지면 패키지 단위로 쪼개기 쉬운 구조를 미리 확보.

**배포 결정**: 로컬 실행(Gradle) + 선택적 Docker Compose(앱+DB 1세트)까지만. **AWS EC2/클라우드 실배포는 하지 않는다** — 공식 제출 요구사항에 배포가 없고(JWT/Docker도 필수 아님), 계정 생성·보안그룹·비용 관리 등 부가 작업이 마감 임박 상황에서 리스크 대비 실익이 없음. (참고: xixvivji 레포는 이미 실배포까지 갔지만 그건 시간 여유가 있었던 상위 1% 사례 — 우리는 P0~P1 완성도에 집중하는 게 맞다). 실배포는 **제출 완료 후, 포트폴리오용으로 하고 싶으면 그때 별도로 진행**하는 걸 권장.

## 4. 사용자 시나리오

1. 운영자가 리소스를 등록한다 (서버/DB/큐/API 타입)
2. 시스템이 5~10초 주기로 각 리소스의 지표(CPU/메모리/에러율/큐길이)를 시뮬레이션 생성
3. 규칙 엔진이 임계치 초과를 감지 → Incident 생성 (심각도 자동 판정)
4. IncidentAgent가 조치(모니터링 강화/재시작 권고/알림/에스컬레이션)를 자동 결정·기록
5. OpenAI API로 판단근거 1~2문장 자연어 요약 생성, Incident에 저장
6. 모든 단계는 AOP가 가로채서 감사로그에 별도 트랜잭션으로 기록 (실패해도 기록됨)
7. 운영자는 API로 사건 목록/상세/집계 통계를 조회하고, 처리 완료된 사건은 resolve 처리

## 5. 성공 기준 (Definition of Done)

- [ ] 지표 이상 발생 → 사건 자동 생성 → 조치 자동 기록 전 과정이 API 호출만으로 재현됨
- [ ] 동시 요청 시 동일 리소스에 중복 사건이 생성되지 않음 (동시성 제어 검증)
- [ ] 의도적으로 실패시킨 요청도 감사로그에 FAIL로 남음
- [ ] Swagger UI에서 전체 API 확인 가능
- [ ] OpenAI 연동 실패 시에도 서비스 전체가 죽지 않고 폴백 문장으로 정상 응답

## 6. 일정 (개요 — 상세는 04_일정관리.md)

애자일 스프린트 방식, 마감 유연 (밤샘 가능) — P0(MVP) → P1(고도화) → P2(부가) 순서로 매 단계마다 커밋 가능한 상태 유지.

## 7. 리스크 & 대응

| 리스크 | 대응 |
|---|---|
| OpenAI API 타임아웃/장애로 전체 흐름 막힘 | 3초 타임아웃 + try-catch 폴백 문장, 별도 스레드/비동기 처리 |

| 심사자가 "이게 진짜 AI냐" 의문 | README에 규칙엔진(결정) vs LLM(자연어 설명)의 역할 분리를 명확히 서술 — 판단은 규칙기반, LLM은 설명만 담당한다고 명시해 과장 방지 |
