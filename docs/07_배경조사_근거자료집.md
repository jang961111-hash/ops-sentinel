# 배경조사 & 근거자료집 (Evidence Dossier) — Ops Sentinel

작성 목적: 이 프로젝트의 모든 설계 결정이 "그냥 그럴듯해 보여서"가 아니라 학술·산업·기업 1차자료에 근거함을 증명. 각 항목은 **출처 등급(1차/2차/3차) · 신뢰도 비판적 평가 · 우리 설계와의 연결점**을 명시.

## 출처 등급 기준
- **1차(Primary)**: 원 발행 기관의 공식 문서/논문/보도자료 (직접 인용 가능)
- **2차(Secondary)**: 1차를 취재·해설한 언론/블로그 (교차검증용, 단독 근거로는 약함)
- **3차(Tertiary)**: 커뮤니티/개인 정리글 (배경 이해용, 근거로 인용 금지)

## A. 학술 근거 — AIOps + LLM 파이프라인

### A-1. AIOps 개념 정의 (1차: Gartner)
- **출처**: Gartner, "Definition of AIOps (Artificial Intelligence for IT Operations)" — [gartner.com](https://www.gartner.com/en/information-technology/glossary/aiops-artificial-intelligence-operations)
- **등급**: 1차 (AIOps 용어를 만든 원 기관)
- **비판적 평가**: Gartner 용어집 페이지는 마케팅성 리서치 요약 링크 위주라 정의 원문이 페이지에 직접 노출되지 않음 — 정확한 인용문은 Gartner 리서치 리포트(유료) 원문 확인 필요. **2차 교차검증**: Splunk, Cisco, IBM 등 벤더 블로그들이 공통적으로 "빅데이터+머신러닝을 IT 운영에 결합해 이벤트 상관분석·이상탐지·근본원인분석을 자동화하는 것"으로 요약 — 여러 독립 소스가 같은 정의로 수렴하므로 신뢰도 높음.
- **연결점**: 우리 프로젝트의 "지표수집→이상탐지→근본원인(규칙)→조치" 파이프라인이 AIOps의 표준 정의 범위 안에 있음을 보여주는 근거.

### A-2. LLM 시대의 AIOps 파이프라인 구조 (1차: 학술논문)
- **출처**: Zhang, Jia, Jia, Yang, Wu, Li (베이징대), *"A Survey of AIOps for Failure Management in the Era of Large Language Models"*, 2024 — [arXiv:2406.11213](https://arxiv.org/html/2406.11213v1)
- **등급**: 1차 (arXiv 프리프린트, 저자·소속 명시된 학술 서베이 논문)
- **비판적 평가**: arXiv는 동료심사 이전 프리프린트 저장소라 정식 저널 게재 심사를 거치지 않았을 수 있음 — 다만 서베이 논문 특성상 인용 트렌드/구조 파악용으로는 충분히 신뢰 가능. 저자 소속(베이징대)과 명확한 방법론 분류가 있어 익명 블로그보다 신뢰도 높음.
- **핵심 인용**: 논문이 제시하는 4단계 파이프라인 — **① 데이터 전처리 → ② 이상탐지(예측/재구성/분류 기반) → ③ 근본원인분석(장애위치·카테고리·보고서생성) → ④ 자동복구(질문지원·솔루션생성·명령추천)**
- **연결점**: 우리 시스템의 `MetricSnapshot → RuleEngine(이상탐지) → Incident(근본원인 카테고리=ruleTriggered) → IncidentAction(자동복구 액션)` 구조가 이 논문의 4단계 파이프라인과 1:1 대응됨. PDF 제출 시 "학계에서 정의한 AIOps 표준 파이프라인을 그대로 구현했다"는 근거로 인용 가능.
- **추가 참고 목록**: [awesome-LLM-AIOps (GitHub, Jun-jie-Huang)](https://github.com/Jun-jie-Huang/awesome-LLM-AIOps) — 관련 논문 큐레이션 리스트 (3차, 추가 탐색용)

### A-3. LLM 기반 근본원인분석(RCA) 실증연구 (1차)
- **출처**: *"Automatic Root Cause Analysis via Large Language Models for Cloud Incidents"* — [arXiv:2305.15778](https://arxiv.org/pdf/2305.15778) (Microsoft 계열 연구로 추정, 원문에서 소속 재확인 필요)
- **등급**: 1차 (실증 논문)
- **연결점**: "LLM이 사건의 근본원인을 요약·설명하는 역할을 실제 클라우드 인시던트에 적용해 효과를 검증"한 선행연구 — 우리 프로젝트의 `aiSummary` 필드(OpenAI가 판단근거를 자연어로 설명)가 학술적으로 검증된 접근 방식임을 뒷받침.

### A-4. 산업 실무 사례 (2차, 참고용)
- Zalando Engineering Blog, *"Dead Ends or Data Goldmines? — Two Years of AI-Powered Postmortem Analysis"* — [engineering.zalando.com](https://engineering.zalando.com/posts/2025/09/dead-ends-or-data-goldmines-ai-powered-postmortem-analysis.html)
- **등급**: 2차이지만 기업 공식 엔지니어링 블로그라 신뢰도 준수(準1차) — 실제 빅테크가 AI 기반 사후분석을 2년간 운영한 결과를 공개
- **연결점**: "AI 요약이 만능은 아니며 실패 사례도 있다"는 균형잡힌 시각 — 우리 README/발표에서 "OpenAI 실패 시 폴백 처리"를 설계한 이유의 실무적 근거로 인용 가능

## B. 산업 거버넌스 표준 — 감사가능성·설명가능성

### B-1. FINOS AI 거버넌스 프레임워크 (1차)
- **출처**: FINOS(Fintech Open Source Foundation), *"Agent Decision Audit and Explainability"* — [air-governance-framework.finos.org](https://air-governance-framework.finos.org/mitigations/mi-21_agent-decision-audit-and-explainability.html), CC-BY-4.0
- **등급**: 1차 (금융권 오픈소스 재단 공식 거버넌스 문서 — Linux Foundation 산하, 골드만삭스·모건스탠리 등 대형 금융기관이 참여하는 컨소시엄)
- **비판적 평가**: 금융서비스 산업 특화 프레임워크라 일반 산업에 그대로 적용은 과확장일 수 있음 — 다만 우리 프로젝트가 "금융 인프라(대신증권)" 사례를 모티브로 하므로 도메인 적합성 높음.
- **핵심 인용**: 4단계 감사 계층(Tier 0~3) 중 **"Tier 2: 명시적 추론 생성 — 명확한 추론이 도구 호출 전에 생성·기록되어야 하며 자연어 설명이 포함되어야 한다"**
- **연결점**: 우리 설계의 "규칙엔진이 먼저 결정(Decision) → LLM이 사후에 자연어 설명(Explanation) 생성 → AOP가 전 과정을 감사로그에 기록"이 FINOS가 제시하는 Tier 2~3 감사 요구사항과 정확히 일치. **PDF 근거자료의 핵심 논거로 사용 권장.**

### B-2. Google SRE Book — 모니터링 원칙 (1차)
- **출처**: Google, *Site Reliability Engineering*, "Monitoring Distributed Systems" 챕터 — [sre.google/sre-book](https://sre.google/sre-book/monitoring-distributed-systems/) (무료 공개, O'Reilly 공동출간)
- **등급**: 1차 (Google 공식 발간, 업계 표준 텍스트로 널리 인용됨)
- **핵심 인용**: **"네 가지 황금 신호(Four Golden Signals)" — 지연(Latency), 트래픽(Traffic), 오류(Errors), 포화도(Saturation)**
- **연결점**: 우리 `MetricSnapshot` 엔티티의 필드(cpuUsage=포화도, memUsage=포화도, errorRate=오류, queueDepth=트래픽/포화도 혼합지표)가 Google SRE의 4대 신호 프레임워크를 그대로 반영한 설계임을 명시 가능. 알림 설계 원칙("조치 가능한가, 실제 영향이 있는가")도 우리 RuleEngine의 임계치 설계 근거로 인용.
