## 1. 커넥션 풀 고갈 — 풀 증설은 문턱만 옮겼다

- **상황**: 2026-08-09, 사전지식 없는 에이전트가 제출 zip을 풀어 서버를 띄우고 채점하는 "콜드스타트 채점"에서, 같은 리소스에 40건을 동시에 보내자 29건이 500으로 끝났다. 실패 감사로그는 0/29건이었다.
- **당시 대응 (2026-08-09)**: H2 락 타임아웃 뒤 Hikari가 커넥션을 폐기하고, 롤백이 `JpaSystemException`으로 감싸져 재시도 catch 목록을 벗어난 것이 직접 원인이었다. 예외 목록을 보강하자 500은 사라졌지만 409 28건과 감사 유실(12/40)이 남았고, 풀을 30→60으로 늘려 40건 조건에서 201 40/40, 감사 40/40(3회)을 맞췄다(`a72514b`, #44). CHANGELOG는 "150건이면 409 91건, FAIL 감사 0건"이라고 적어 두었다.
- **영향**: README는 이 결과를 "완전히 해결", "감사로그 100%"로 적었다. 풀 60은 H2 인메모리 기준으로도 큰 값이다.
- **가설 (2026-09-28)**:
  1. 락 안의 OpenAI 호출이 락 보유 시간을 AI 응답 시간만큼 늘린다. 제출본은 `Resource` 비관적 락을 쥔 트랜잭션 안에서 `aiSummaryService.summarize`를 불렀다.
  2. 락 안의 `@Auditable`(REQUIRES_NEW)이 커넥션을 하나 더 빌린다. 락 대기자가 풀을 다 쥐면 락 보유 스레드가 멈춘다.
  3. 풀 크기가 부족하다(당시의 가설). 맞다면 60이면 버텨야 한다.
- **검증**:
  - 가설 1: AI 지연 3초를 주입하자 같은 리소스 20건 **전부**가 3.05초를 기다렸다. 락을 쥔 1건만 AI를 부르고 나머지 19건은 기존 사건을 돌려받는데도 그랬다. 처리량은 340 → 6.6 rps. 연결·읽기 타임아웃이 각각 3초라 최악(CONNECT 2.9s + 응답 2.9s)에는 5.86초 동안 락을 쥐었다. → 채택.
  - 가설 2: 풀 30·40건·AI 지연 0초에서 3/3라운드가 붕괴했다. 라운드마다 Hikari active 30/30 + pending 12~13, 지연 10.4s(= H2 락 타임아웃), 409 28~29건. 키가 없어 AI를 전혀 부르지 않는 조건에서도 1/3라운드가 같은 모양으로 붕괴했다. → 채택. AI 호출은 이 교착을 "가끔"에서 "항상"으로 바꾸는 증폭기였다.
  - 가설 3: 풀 60에서도 150건이면 409 91~93건, 감사 38~39%로 붕괴했다. → 기각. 버티는 한계는 대략 "동시 대기 요청 수 < 풀 크기 − 1"이었다.
  - 남은 의문: 409 요청의 **실패** 기록은 트랜잭션 밖에서 남는데 왜 0건인가. 서버 로그의 `Caused by`를 세자 `Timeout trying to lock table`은 409 요청당 1회(87건)뿐이고, `JDBC begin transaction failed: Connection is closed`가 174건(= 87 × 감사 2건), `재시도합니다`가 261건(= 87 × 3)이었다. 락 타임아웃 뒤의 재시도 3회와 감사 2건이 모두 **이미 닫힌 커넥션**으로 실패하고 있었다.
- **원인**: 세 가지가 겹쳤다.
  1. 락 안의 AI 호출 (락 보유 시간 = AI 응답 시간)
  2. 락 안 REQUIRES_NEW 감사의 커넥션 교착
  3. Spring Boot 기본값 `spring.jpa.open-in-view=true`: 요청 스레드가 처음 쓴 커넥션을 응답 끝까지 쥐고(`DELAYED_ACQUISITION_AND_HOLD`), 트랜잭션 밖 REQUIRES_NEW도 그 EntityManager를 재사용한다. H2 락 타임아웃 뒤 Hikari가 그 물리 커넥션을 폐기하면 같은 요청의 후속 작업이 모두 죽은 커넥션을 썼다. 기동 로그에는 `spring.jpa.open-in-view is enabled by default` 경고가 계속 찍혀 있었다.
- **해결** ([PR #48](https://github.com/jang961111-hash/ops-sentinel/pull/48)): 재현 테스트 3종을 먼저 커밋해 수정 전 실패를 확인했다(`3984014`).
  - AI 요약: 폴백 문구를 먼저 넣어 커밋하고, `IncidentCreatedEvent` → `@TransactionalEventListener(AFTER_COMMIT)` 리스너가 전용 풀(2~4 스레드, 큐 200)에서 요약한 뒤 `UPDATE`한다(`5781004`).
  - OSIV 끔, 트랜잭션 안 감사는 같은 트랜잭션에(`MANDATORY`), 트랜잭션 안 실패는 롤백이 끝난 `afterCompletion`에서 REQUIRES_NEW로 기록(`8d69faa`). 이 시점에는 락이 이미 풀려 있어 커넥션을 기다려도 교착이 되지 않는다.
  - 락 없는 사전 조회: OPEN 사건이 있으면 락을 타지 않는다(double-checked, `4411283`).
  - 풀을 60에서 기본값 10으로 되돌림(`347de65`).

## 2. "감사로그 100% 기록"이 거짓이었다

- **상황**: 제출 README와 발표문은 "모든 단계를 성공·실패 여부와 함께 AuditLog에 100% 기록"한다고 적었다. 40건 회귀 테스트는 예외가 없는지만 보고 감사 건수는 검사하지 않았다.
- **영향**: 이 프로젝트의 핵심 가치("판단을 사후에 검증할 수 있다")와 정면으로 어긋난다.
- **가설**: 감사 기록도 DB 커넥션이 필요하므로, 커넥션 경합이 생기는 순간에 기록이 빠진다.
- **검증** (2026-09-28): 부하 스크립트가 라운드마다 고유 마커(예: cpuUsage 95.00x)를 넣고 감사로그를 마커로 매칭해 셌다. AI 지연 3초·풀 60·150건에서 3라운드 모두 감사 57~58/150건(38~39%), FAIL 감사 0건. AI 지연이 없을 때도 1/3라운드에서 409 91건·FAIL 감사 0건·"AuditLog 기록 자체가 실패" 로그 182건(= 91 × 2)이 나와, CHANGELOG `[1.0.2]`의 당시 기록과 숫자까지 같았다. 409로 끝난 요청은 성공 기록도 실패 기록도 없었다.
- **원인**: 1번의 OSIV 닫힌 커넥션 재사용과 락 안 REQUIRES_NEW 교착. 여기에 하나가 더 있었다. FAIL 감사의 `errorMessage`를 컬럼 길이(2000자)로 자르지 않아, 긴 예외 메시지가 오면 INSERT가 실패하고 `recordSafely`가 그 실패를 삼켜 FAIL 감사가 조용히 사라졌다(리뷰 재검토에서 발견).
- **해결**: 1번의 수정 + 2,500자 예외를 던지는 테스트 전용 `@Auditable` 빈으로 수정 전 0건을 재현(`3407002`)한 뒤 2000자 절삭(`c76c37c`).
- **결과**: 동시 150건 감사 기록률 38.2% → 100%(450/450), 풀 10에서도 450/450. 긴 예외 메시지의 FAIL 감사 0건 → 1건(2000자).
- **trade-off**: 락 트랜잭션 안의 `INCIDENT_ACTION_DECIDE` 성공 기록은 이제 사건·조치 행과 **함께 커밋되거나 함께 롤백된다.** 롤백된 트랜잭션의 성공 기록은 남지 않는다(애초에 성공하지 않았으므로). 그 요청의 실패는 트랜잭션 밖의 `INCIDENT_DETECT`·`METRIC_SIMULATE` 어드바이스가 기록한다. 또 7초 스케줄러의 지표 생성은 처음부터 감사 대상이 아니다. 그래서 README에는 "100%"가 아니라 "측정 조건에서 요청 수와 일치"라고 쓴다.
- **재발 방지**: `AuditInTransactionTest` 2건이 새 감사 의미를 고정한다. `NarrowPoolAuditTest`의 409 유도 테스트가 METRIC_SIMULATE FAIL 감사 1건을 단언한다(수정 전 0건).
- **배운 점**: "실패해도 감사는 남는다"는 설계(REQUIRES_NEW)가 정확히 필요한 순간, 즉 커넥션이 부족한 순간에 무너졌다. 감사 건수를 세는 테스트가 없으면 이 주장은 검증된 적이 없는 것이다.

## 3. CI(Linux)에서만 실패한 해결 시각 멱등성 테스트

- **상황**: PR #48에 GitHub Actions를 붙인 첫 실행에서 `IncidentQueryServiceTest` 1건이 실패했다. 로컬(macOS)에서는 52/52 통과였다.
- **가설**: 1) 비동기 요약 도입으로 생긴 타이밍 문제 2) 플랫폼 차이.
- **검증**: CI 아티팩트의 HTML 리포트에 `expected 2026-09-28T07:37:52.594615505 but was 07:37:52.594616`이 있었다. 타이밍이 아니라 정밀도 차이였다.
- **원인**: Linux JVM의 `LocalDateTime.now()`는 나노초까지, macOS JVM은 마이크로초까지 준다. H2 `TIMESTAMP`는 마이크로초로 반올림해 저장한다. 첫 `resolve`가 돌려준 메모리 값과, 두 번째 `resolve`가 DB에서 읽은 값이 달랐다.
- **해결**: 테스트가 아니라 운영 코드에서 `now().truncatedTo(ChronoUnit.MICROS)`로 저장값과 반환값을 맞췄다(`3aed33e`).
- **결과**: CI 1차 실패 → 통과(run 36392869316).
- **배운 점**: CI를 붙인 첫 실행이, 로컬에서는 한 번도 드러나지 않던 플랫폼 의존 버그를 잡았다.

## 4. 리뷰가 잡은 비동기 요약 덮어쓰기와 감사 실패 500

PR #48을 별도 리뷰 에이전트에 검토시켰다. 1차 결과는 HIGH 1(PR 본문이 다른 작업 내용으로 덮어써진 사고)·MED 3·LOW 3이었고, 반영 후 재검토에서 승인을 받았다. 코드 결함 MED 2건:

- **비동기 요약이 폴백 문구로 되돌아감**
  - 원인: 요약 저장은 벌크 `UPDATE`라 `@Version`을 올리지 않는다. 그 전에 사건을 읽은 트랜잭션(예: `resolve`)이 커밋하면 Hibernate가 전체 컬럼을 UPDATE해서 요약을 덮어쓴다.
  - 재현: 사건 읽기 → 다른 스레드가 요약 저장 → 상태 변경 커밋 → `expected "AI 요약" but was "폴백 문구"`(`4ec2251`, 수정 전 실패).
  - 해결: `@DynamicUpdate`(바뀐 컬럼만 UPDATE, `74554b8`). 요약 UPDATE에서 `version = version + 1`을 올리는 방법은 `resolve` 커밋을 낙관적 락 실패로 만들어 버렸다.
- **트랜잭션 안 감사 실패가 500으로 샘**
  - 원인: 같은 트랜잭션에 참여한 감사 저장이 DB 오류로 실패하면, recorder가 예외를 삼켜도 트랜잭션은 이미 rollback-only다. 커밋에서 `UnexpectedRollbackException`이 났고 재시도 목록에 없었다.
  - 재현: `@SpyBean AuditLogRecorder`로 첫 호출만 실제 제약 위반(action NULL)을 일으킴 → 수정 전 예외 전파. 스텁 설정 호출 자체도 `MANDATORY` 어드바이스를 타서 `No existing transaction found`가 났기 때문에, 스텁 설정을 `TransactionTemplate` 안에서 했다.
  - 해결: 재시도 목록에 추가(`2d04c17`). 두 번째 시도에서 성공한다.
  - 한계: 감사 실패가 매번 일어나면 재시도 3회 뒤 409 + 트랜잭션 밖 FAIL 감사로 끝난다. 세이브포인트(NESTED)로 격리하는 방법은 JPA/Hibernate 지원이 불확실해 범위 밖으로 뒀다.
- **결과**: 두 재현 테스트 실패 → 통과. 테스트 52 → 56건, CI 통과(run 36394914567).
- **배운 점**: 동시성 수정이 새 동시성 경로(커밋 후 비동기 쓰기)를 만들었다. 수정 PR도 같은 기준으로 리뷰를 받아야 했다.

## 5. 감사로그가 존재하지 않는 사건을 가리켰다 (2026-08-09, C1)

- **상황**: 별도 리뷰 에이전트의 최종 검증에서 REJECTED 판정을 받은 결함 5건(C1~C5) 중 하나. 서버를 막 띄우고 정상 지표로 시뮬레이션을 1회 호출하자, 존재하지 않는 Incident id를 가리키는 감사로그가 생겼다.
- **원인**: `AuditLogAspect.extractTargetId`는 반환값에서 id를 못 찾으면 메서드 인자 중 아무 `getId()`나 썼다. `detectAndCreate`가 정상 지표(약 90%)에서 `Optional.empty()`를 돌려주면, 인자로 받은 `MetricSnapshot`의 id가 `targetType="Incident"`의 targetId로 기록됐다.
- **해결**: 반환 타입이 `Optional`이면 그 값을 그대로 믿는다. `Optional.empty()`는 "대상 없음"으로 보고 인자에서 id를 찾지 않는다(`1428c09`, #36).
- **결과**: 리뷰 에이전트 재검증에서 APPROVED(`CHANGELOG.md` `[1.0.1]`). 다만 "정상 지표일 때 INCIDENT_DETECT 감사의 targetId가 null"을 따로 단언하는 회귀 테스트는 아직 없다(후속 과제).
- **같은 검증에서 고친 것**: 감사 기록 실패가 원래 예외를 덮어쓰던 문제(C2), 프레임워크 예외가 500으로 응답되던 문제(C3), H2 전용 `DATEDIFF`가 PostgreSQL에서 깨지던 문제(C4), README가 완료된 기능을 미착수로 적던 문제(C5), `HEAD` 요청으로 JWT 보호를 우회하던 문제(M2). 상세는 `CHANGELOG.md` `[1.0.1]`.
- **배운 점**: 감사로그의 "대상"이 틀리면 기록이 남아도 감사가 되지 않는다. 기록 여부만큼 기록 내용도 검사해야 한다.
